Reproduce the current focused suite:

```sh
WAYPOINT_OCI_CORPUS=1 \
WAYPOINT_HELM_BIN=/tmp/waypoint-implementation/helm-tool/linux-amd64/helm \
pnpm exec tsx --test \
  tests/server/import-audit.test.ts \
  tests/server/oci-corpus.test.ts \
  tests/server/helm-environment.test.ts \
  tests/server/repository-import.test.ts \
  tests/domain/deployment-plan.test.ts \
  tests/domain/dependency-analysis.test.ts
```

`WAYPOINT_OCI_CORPUS=1` opts into a bounded public OCI download/render check. Without that flag, its test is skipped and is **NOT RUN**, not a pass. The tool path above identifies this machine's trusted installed Helm; substitute a supported installed Helm path elsewhere.

The Docker fallback regression reproduced a real trust boundary before the fix: a synthetic native credential helper was invoked during successful public OCI rendering despite an explicit registry configuration. [Pre-fix output](/tmp/waypoint-audit-docker-fallback-before.log). No actual credential store or native helper was used in that test. Current checks pass with private credential-free configuration in both stores. The nonempty `.invalid` auths entry contains no credential and prevents default helper detection. This follows the actual [Helm 4.3.0 registry fallback](https://github.com/helm/helm/blob/v4.3.0/pkg/registry/client.go), its [pinned ORAS dependency](https://github.com/helm/helm/blob/v4.3.0/go.mod), and ORAS's [store detection](https://github.com/oras-project/oras-go/blob/v2.6.2/registry/remote/credentials/store.go) and [configuration detection](https://github.com/oras-project/oras-go/blob/v2.6.2/registry/remote/credentials/internal/config/config.go). This isolates credential stores; it is not a general network or process security sandbox.
